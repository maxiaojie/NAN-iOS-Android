# TB323FU：连接普通 Wi-Fi 后 NAN Publish 尾部异常，iOS 无法发现

记录日期：2026-11-13。设备 TB323FU，Android 17；对端 iPhone 12，iOS 27.0。此问题交由平板 ROM 流程继续定位，应用侧暂以断开普通 Wi-Fi、保留 Wi-Fi 开关进行互通测试。

## 现象和对照

| 状态 | Publish 帧尾 | iOS 发现 |
| --- | --- | --- |
| 平板连接普通 Wi-Fi（本轮曾连接 lenovo-internet，5260 MHz） | 完整 Vendor Specific 属性后额外 23 字节 00 | 本轮持续失败，原/新 App 均出现 |
| 平板断开普通 Wi-Fi，Wi-Fi 开关保持开启 | 用户抓包确认额外 23 字节消失 | 恢复，USB 截图确认显示平板设备名 |
| Pixel 9 连接普通 Wi-Fi（RD-Test，5320 MHz） | 对照 Publish 无该额外尾部 | 正常，旧/新 App 均可发现 |

平板曾在前一天成功被发现、配对、建立链路，故不是设备完全不支持 NAN。不能把本问题描述成所有 Android 或 Wi-Fi Aware 都不能与普通 Wi-Fi 共存。

原始字节逐项对照见 [Publish 报文比较](packet-comparison-2026-11-13.md)。昨天 3.pcapng 的 10 个平板 Publish 无额外尾部；今天 ch6-20261113-100114-82604.pcap 的 70 个平板 Publish 均有额外尾部。该两份抓包还存在 SSI 和 Availability 内容变化，不能仅靠这两份跨时间抓包完成单变量因果证明。

关闭配对缓存/验证、缩短设备名、清除旧测试配对均未单独恢复发现，临时 App 改动已撤销。断开普通 Wi-Fi 后，当前正式配置的新 App 能进入系统 PIN 配对流程。

## ROM 排查方向（假设，尚未证实）

1. 比较 STA 连接和断开时 NAN SDF 长度计算、缓冲区初始化及实际发送长度，尤其是附加 Vendor Specific 属性和并发调度属性的拼接。
2. 检查 STA + NAN 模式下是否保留或预留了未写入的 23 字节区域。
3. 分别验证路由器 2.4 GHz、5 GHz 的不同信道与带宽组合，区分并发模式通用问题和特定信道组合触发。
4. 在驱动实际发送缓冲区与独立 monitor 抓包之间核对长度，并尽可能查明 iOS 驱动是否因属性格式拒收。Wireshark 的 Malformed 提示本身不能证明 iOS 的实际过滤分支。

## 当前结论边界

“普通 Wi-Fi 连接状态、额外尾部、发现结果”在用户切换测试中同步变化，强烈指向 TB323FU 当前 STA + NAN 并发路径。尚未定位具体源码行，也未证明单独去掉 23 字节即可修复所有连接场景。Pixel 对照说明需要聚焦平板实现及其具体并发条件。

发现恢复后出现的 `Network.NWError -11987` 是另一个阶段的问题：系统配对已成功，随后 NDP 建立失败，Android 驱动记录原因码 9010。应用数据尚未开始收发，后续继续单独排查数据链路。

## 异常具体位置与原始字节

下面偏移均从 NAN Action body 的第一个字节（`04 09 50 6f 9a 13`）开始，以 **0 为起点**。NAN 属性头为 1 字节 ID + 2 字节 little-endian 长度；长度字段只计算属性内容，不含 3 字节头。

平板帧 530 的相关属性布局：

| body 偏移（十进制） | 属性 ID | 内容长度 | 下一个属性偏移 |
| --- | --- | --- | --- |
| 131 | 3：Service Descriptor | 69 | 203 |
| 203 | 14：Service Descriptor Extension | 68 | 274 |
| 274 | 34：Cipher Suite Info | 5 | 282 |
| 282 | 35：Security Context Info | 20 | 305 |
| 305 | 11：Country Code | 2 | 310 |
| 310 | 44：Pairing Bootstrapping | 5 | 318 |
| 318 | 43：NAN Identity Resolution | 17 | 338 |
| 338 | 221：Vendor Specific，类型 0x41 | 33 | 374 |
| 374 | 221：Vendor Specific，类型 0x33 | 14 | **391，正常属性应在这里结束** |
| **391～413** | **额外 23 字节 00** | 不构成合法属性序列 | body 实际结束于 414 |

该帧 Radiotap 56 字节，802.11 管理帧头 24 字节，Action body 起点为整个捕获帧的偏移 80。因此多余数据位于整个帧 **471～493**（同样从 0 计数）。

从 body 偏移 338 起的原始结构如下（每行不是 Wireshark 自动推断，而是依据长度字段切分）：

```text
dd 21 00                         # 属性 ID 221，内容长 0x0021 = 33
00 00 f0 41                     # OUI 00:00:f0，类型 0x41
1b 00 ff 19 6c 00 00 e2 ff ff 01 00 06 00 00 02
22 22 22 22 22 22 22 22 22 12 00 00 00

dd 0e 00                         # 属性 ID 221，内容长 0x000e = 14
00 00 f0 33                     # OUI 00:00:f0，类型 0x33
08 00 01 00 00 00 00 00 00 00

00 00 00 00 00 00 00 00         # 以下才是额外 23 字节
00 00 00 00 00 00 00 00
00 00 00 00 00 00 00
```

最后一个 Vendor Specific 属性的合法内容本身以 7 个零字节结尾；额外部分是它之外的另外 23 字节，不能通过简单统计文件末尾零字节数量来判断。

Wireshark 对额外部分的解析：7 个 `Master Indication Attribute (ID 0, Length 0)`，每个占 3 字节头且报 `Element length invalid`，剩余 2 字节报 `Insufficient remaining packet bytes for NAN attribute`。这些零字节不是 SSI 内部 TXT 的尾部，也不是最后一个厂商属性长度所包含的内容。

昨天帧 265：最后两个厂商属性内容逐字节相同，分别位于 body 偏移 358、394，最后属性结束于 **411**，body 长度也是 **411**，没有额外部分。Pixel 帧 950：body 长 **256**，最后一个属性结束于 **256**，没有额外部分。

## 已排查的变量与限制

- 服务 ID、SDEA `0x0440`、PIN Display、上述两个厂商属性，在昨天和今天的平板报文中相同。
- Pixel 同样为 SDEA `0x0440`，`Data Path Required=false` 且 `Security=true`，仍可被 iOS 发现，不能把该位直接认定为发现失败原因。
- 长设备名不是必要触发条件：将平板 pairingName 暂改为 7 字符 `TB323FU`，仍复现额外尾部和发现失败；正式配置已恢复系统设备名称。
- 将新 App 临时改用原示例服务名进行对照，仍复现。正式代码已恢复 `_aware-bridge._udp`。
- 新旧 App 对照与同一个旧 APK 跨设备对照都执行过；后者平板对应抓包窗口没捕获到 Publish，不能用于证明其发出了相同坏帧。
- 关闭配对缓存和验证后，NIRA 属性减少 20 字节（3 字节头 + 17 字节内容），额外 23 字节仍在，iOS 发现未恢复。
- 已清除旧 App 的一条测试配对；没有删除普通 Wi-Fi 保存网络。没有证据证明缓存密钥就是发现失败根因。
- Pixel 在连接 RD-Test 的情况下正常发现，证明“连接普通 Wi-Fi”不是所有设备上的普遍禁止条件；平板和 Pixel 的 AP 信道不同，尚不能排除 AP 信道/带宽这一变量。
- 平板断开 Wi-Fi 后尾部消失来自用户当前抓包确认；本文作者已直接通过 USB 截图确认恢复发现和进入 PIN 流程。10:30 与 10:32 新采集窗口未含 Publish，不能伪称已用这些空窗口独立验证尾部消失。

## 建议的 ROM 复现与验收

保持同一 App 二进制、同一 iPhone、相同距离和服务配置，分别记录“连接 AP → 断开 AP → 再次连接 AP”至少三轮。每轮重新打开 iOS DevicePicker并覆盖实际 Publish 所在信道，记录发现时间、STA 信道/带宽、NAN 信道、frame.len 和最后属性结束位置。再分别改变 AP 2.4 GHz / 5 GHz、信道和带宽。

在 HAL/驱动/固件边界同时记录准备发送的缓冲区长度与最终管理帧长度，检查 STA 并发分支是否把预留容量当成有效长度。若能仅修正帧长度、保留其他字段和并发状态后恢复 iOS 发现，才可把异常尾部和过滤行为建立更强因果联系。

修复验收应包括：STA 连接情况下 Publish 属性边界完整，iOS 稳定发现；完成 PIN 配对和缓存验证；完成 NDP 协商；两端应用收到 UDP 与 ACK。后续 `-11987`/9010 属于 NDP 阶段，不能用“发现成功”替代数据链路验收。
