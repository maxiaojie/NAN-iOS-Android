# TB323FU：连接普通 Wi-Fi 后 NAN Publish 尾部异常，iOS 无法发现

记录日期：2026-11-13。设备 TB323FU，Android 17；对端 iPhone 12，iOS 27.0。此问题交由平板 ROM 流程继续定位，应用侧暂以断开普通 Wi-Fi、保留 Wi-Fi 开关进行互通测试。

## 现象和对照

| 状态 | Publish 帧尾 | iOS 发现 |
| --- | --- | --- |
| 平板连接普通 Wi-Fi（本轮曾连接 lenovo-internet，5260 MHz） | 完整 Vendor Specific 属性后额外 23 字节 00 | 本轮持续失败，原/新 App 均出现 |
| 平板断开普通 Wi-Fi，Wi-Fi 开关保持开启 | 用户抓包确认额外 23 字节消失 | 恢复，USB 截图确认显示平板设备名 |
| Pixel 9 连接普通 Wi-Fi（RD-Test，5320 MHz） | 对照 Publish 无该额外尾部 | 正常，旧/新 App 均可发现 |

平板曾在前一天成功被发现、配对、建立链路，故不是设备完全不支持 NAN。不能把本问题描述成所有 Android 或 Wi-Fi Aware 都不能与普通 Wi-Fi 共存。

原始字节逐项对照见 [Publish 报文比较](packet-comparison-2026-11-13.md)。昨天 3.pcapng 的 10 个平板 Publish 无额外尾部；今天 ch6-20261113-100114-82604.pcap 的 70 个平板 Publish 均有额外尾部。该两份抓包还存在 SSI 和 Availability 内容变化，不能仅靠这两份跨时间抓包完成单变量因果证明。

关闭配对缓存/验证、缩短设备名、清除旧测试配对均未单独恢复发现，临时 App 改动已撤销。断开普通 Wi-Fi 后，当前正式配置的新 App 能进入系统 PIN 配对流程。

## ROM 排查方向（假设，尚未证实）

1. 比较 STA 连接和断开时 NAN SDF 长度计算、缓冲区初始化及实际发送长度，尤其是附加 Vendor Specific 属性和并发调度属性的拼接。
2. 检查 STA + NAN 模式下是否保留或预留了未写入的 23 字节区域。
3. 分别验证路由器 2.4 GHz、5 GHz 的不同信道与带宽组合，区分并发模式通用问题和特定信道组合触发。
4. 在驱动实际发送缓冲区与独立 monitor 抓包之间核对长度，并尽可能查明 iOS 驱动是否因属性格式拒收。Wireshark 的 Malformed 提示本身不能证明 iOS 的实际过滤分支。

## 当前结论边界

“普通 Wi-Fi 连接状态、额外尾部、发现结果”在用户切换测试中同步变化，强烈指向 TB323FU 当前 STA + NAN 并发路径。尚未定位具体源码行，也未证明单独去掉 23 字节即可修复所有连接场景。Pixel 对照说明需要聚焦平板实现及其具体并发条件。

发现恢复后出现的 `Network.NWError -11987` 是另一个阶段的问题：系统配对已成功，随后 NDP 建立失败，Android 驱动记录原因码 9010。应用数据尚未开始收发，后续继续单独排查数据链路。
